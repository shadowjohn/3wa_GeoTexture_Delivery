## 建議逐項判斷

| 原編號 | 判斷 | 調整後的做法 |
| --- | --- | --- |
| 1.1 批次 Python | 採用，與全量重掃修正一起做 | 每批共用一個 Python 行程，逐棟回報成功/失敗；不能等整批完成才更新進度。保留取消、時間預算與單棟故障隔離。 |
| 1.2 移除中繼 JSON | 程序化路徑採用 | 建議 PHP 經 stdin 傳有界資料、Python 經 stdout 回傳逐棟結果。PHP 繼續負責任務狀態和成果登錄。先保留實景轉換所需的檔案輸入及舊 CLI 相容性。 |
| 1.3 逾時清除鎖檔 | 不採用刪鎖檔 | 目前是作業系統 `flock`，不是用檔案存在與否當鎖。可補執行時間、PID 與逾時診斷，但不能用檔案年齡判定死鎖並 unlink。 |
| 2.1 共用 Texture Atlas | 採用，需真正共用 GPU 資源 | 不能只把同一張圖重複內嵌進每個 GLB。圖集、材質去重、UV 邊界及分塊模型必須一起設計。 |
| 2.2 整區合併 GLB | 採用，放在材質/primitive 優化之後 | 合成一個檔案不會自動降低 Draw Call。需統一區域原點、轉換各棟局部座標、依相容材質合併幾何，保留建物對照及原始單棟成果。大型匯出應避免壓在同步 HTTP 請求中。 |
| 2.3 圖台分塊 | 採用 | 以有限大小區塊共用幾何/材質，保留視野裁切與版本失效機制。沿用 footprint 圖層做點選；不要把整座城市變成永遠常駐的一個模型。 |
| 3.1 垂直三段式 | 採用，建立新的風格版本 | 一樓、標準層、屋頂帶依實際高度分配；低矮建物不能硬塞固定高度的三段。騎樓陰影可以是示意，真正挖入騎樓幾何需另外處理輪廓意義。 |
| 3.2 整數開間 UV | 採用，但公式需配合圖樣 | 現有每張立面圖有兩個開間，不能直接把整張圖重複 N 次當作 N 扇窗。狹窄碎邊應留實牆或合併共線段，並保留窗框邊距。 |
| 3.3 屋突/水塔 | 後續可選的示意細節 | 內縮可能得到空集合或多塊；需處理內洞、狹長屋頂與碰撞。原始高度和合成附屬物高度分別記錄，不能把隨機屋突說成實測建物。 |
| 3.4 PBR | 修正描述後採用 | 現有模型已用 PBR，台灣/粉彩牆面 roughness 為 0.88、現代為 0.48。缺的是玻璃與牆面的分區材質反應，可用 roughness/metalness 貼圖或材質分組；不能只改全牆一個參數。粉彩插畫的手繪反光可保留。 |
| 4.1 實景混合補面 | 校準與品質模型完成後再接 | 須逐面區分照片觀測、程序化補面和缺面，分開計算「外觀覆蓋」與「實景覆蓋」。程序化補齊不能讓尚未校準的照片變成已驗證。 |
| 4.2 牆角校準 | 作為實景路線的前置工作 | 沿用既有交接，先核對可信三維/影像對應，再以獨立點檢查誤差。四點求解成功本身不是貼圖對位通過驗收。 |

## 原文件漏掉的優先修正

### 每棟完成後重掃全部任務

`src/App.php` 的 `registerResult()` 登錄每一棟成果後呼叫 `jobs()`；`runBatch()` 又對目前任務呼叫 `job()`。這些流程會查詢大量項目並重新讀取既有模型、核對 hash。隨著成果累積，單棟處理成本持續增加，單純重用 Python 行程無法解決。

建議把逐棟更新限制在本次受影響的任務與計數，全量損壞/遺失成果核對改成有界、較低頻率的工作。重疊任務、強制重做、取消、partial 狀態、缺檔重新排隊及登錄驗證都要保留。不能為了快而把成果存在與完整性檢查全部拿掉。

批次 Python 應先使用有界的資料流；stdout 是逐棟結構化結果、stderr 是診斷。PHP 必須同時處理管道，避免輸出塞滿造成互等，並在單棟逾時、取消及批次時間到達時正確收尾。這不需要先導入常駐服務、Redis 或另一套排程器。

### 每面牆各自是一個繪製單元

`pipeline/procedural.py` 在每面牆呼叫 `glb.primitive(group)`；牆面即使用相同材質，也各有獨立 primitive。glTF 的 primitive 對應 GPU 繪製所需資料，因此把多個 GLB 包成單一 GLB 並不等於自動變成一、兩次 Draw Call。[glTF 規格](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#meshes)

先驗證把同棟相容牆面合併成少量材質組的收益，再處理跨棟圖集與區塊。現有 PHP 品質驗證讀取 primitive 上的 `wall_key`，所以幾何合併必須保留逐面的三角形範圍/來源對照，並相容舊 manifest，不能直接丟掉面級證據。

### 鎖檔不等於持鎖狀態

既有 `worker.lock` 不會逐棟更新修改時間。用「60 秒沒有修改」刪除它，可能刪掉仍被合法 worker 持有的檔案；新程序再開同名檔案，會造成兩個不同檔案的鎖並存，失去原本互斥的目的。

`flock` 在檔案描述元關閉時釋放；本機 SIGKILL 測試也證實可重新取得鎖。仍存活但卡住的 worker 或持鎖描述元被其他程序持有，應從程序/子程序生命週期與逾時處理診斷，不能靠刪除路徑推定恢復。[PHP flock 手冊](https://www.php.net/manual/en/function.flock.php)

## 調整後執行順序與驗收

| 順序 | 工作 | 驗收依據 |
| --- | --- | --- |
| 1 | 移除逐棟全量重掃；加入有界批次 Python 與逐棟結果回報 | 同一組來源與相同既有成果量，比較完整 worker 的時間/棟與峰值記憶體。取消、失敗重試、強制重做、跨任務重用、遺失檔案及 AJAX 進度仍正確。不能只測 Python 空迴圈。 |
| 2 | 同材質 primitive 合併、面級對照與品質格式相容 | 以相同建物和固定相機比較 primitive 數、實測 Draw Call、載入時間；內洞、法線、輪廓、高度與面積核對通過。 |
| 3 | 小範圍共用圖集與區塊模型試作，再接整區 GLB 匯出 | 量測實際 GPU 紋理數、記憶體與幀時間；確認各棟位置/選取 ID、來源授權、遺失成果清單和軸向。保留單棟原始成果供追查。 |
| 4 | 整數開間 → 樓層分區 → 分區 PBR → 可選屋突 | 先選不同寬度、高度、凹形和有內洞的代表建物比較。建立新 style/recipe 版本；保留舊風格與使用者選擇。圖集設計時先預留這些分區，降低重做成本。 |
| 5 | 可信控制點校準 → 實景面與程序化面混合 | 使用獨立控制點及可重現的投影結果驗收，保存逐面來源與品質；匯出明確標示 synthetic/observed/missing，不能混算實景完成率。 |

若目的優先是交付多種可選風格，前四項即可持續產生可交付成果；實景校準不應阻塞程序化路線。原文件的工時與百分比暫列目標，待代表性端到端樣本完成後再估算。
